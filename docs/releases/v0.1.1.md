# SPA v0.1.1

Semantic Prompt Architecture v0.1.1 is a maturity release built on the SPA Core v0.1 architecture.

It does not redefine the fundamental Core semantic model.

The release strengthens evidence that the Core boundary can support multiple independent semantic domains while preserving deterministic translation and explicit Unknown semantics.

## Highlights

### Third reference domain

Research Evidence was added as a third independent SPA Domain Adapter.

This provides additional evidence that the shared Core architecture can support substantially different semantic problem spaces without introducing domain-specific vocabulary into Core.

### Third-domain validation

The repository records the results of validating SPA Core against the Research Evidence domain.

The validation supports the current Core boundary rather than motivating immediate Core expansion.

### Versioning policy

SPA now documents how Core, Domain Adapters, translators, and related components should evolve and be versioned.

### Core Expansion Proposal process

A governance process now exists for proposed changes to SPA Core.

Core expansion should be driven by evidence across domains rather than convenience within a single adapter.

### Developer Quickstart

A developer guide documents the shortest path from:

~~~text
Semantic Schema
↓
Options
↓
Selection Resolution
↓
Semantic State
↓
Canonical State
↓
Translator
↓
Prompt IR
↓
Renderer
~~~

### Copyable Starter Adapter

The Meeting Preference example provides a minimal runnable Domain Adapter.

It demonstrates that a developer can use SPA from outside Core, pass the Domain Adapter Conformance Kit, and render a prompt without modifying SPA Core.

## Compatibility

SPA v0.1.1 preserves the SPA Core v0.1 architectural direction.

This release primarily improves:

- cross-domain validation
- governance
- developer onboarding
- executable examples
- evidence for the current Core boundary

## Architectural Direction

The central SPA principle remains:

> Represent meaning first. Generate prompts from meaning.

Domain-specific needs should remain in Domain Adapters unless repeated evidence across substantially different domains demonstrates a genuine Core-level requirement.
